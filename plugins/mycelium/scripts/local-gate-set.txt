# THE FRAMEWORK-DEV GATE SET — one source of truth for CI and the pre-push hook.
#
# WHY THIS FILE EXISTS
# -------------------
# Until v0.110.0 the gate list lived in two hand-maintained places: the steps in
# `.github/workflows/validate.yml` and a hard-coded run of four scripts inside
# `scripts/git-pre-push-example.sh`. Measured 2026-08-09 they had drifted to
# **11 in CI against 4 in the hook** — seven gates that could only ever go red
# after a push. That is the precise failure `corrections.md` recorded on
# 2026-06-18 ("Local validation != CI gates"), whose own prevention rule was
# "when adding a CI-only gate, add it to the pre-push hook OR document the
# run-locally step in the same commit". The rule was followed for the gate that
# motivated it and for nothing after: seven later gates went to CI alone.
#
# A hand-maintained list in two files diverges. It is not a discipline problem;
# it is two lists. So there is one list, here, and `check_gate_parity.py`
# asserts that every check invoked in CI appears in it.
#
# FORMAT
#   <script-name>[ <args>]      one gate per line; `#` starts a comment
#   !waived <script-name> <reason>   a CI gate deliberately NOT run locally
#
# A waiver needs a reason on the same line. The alternative to supporting
# waivers is that the first genuinely CI-only gate gets "fixed" by deleting the
# parity check, and then nothing watches the list at all.
#
# SCOPE: framework development only. The hook runs this set solely when
# `tests/python/` is present; a downstream project consuming the plugin never
# reaches it.

# ADDED 2026-09-22. Asserts the CURRENT version has a changelog section, and nothing
# else. `--check` cannot live here: it also requires every documented version to have a
# Release, which is false by construction between the bump commit and the merge that
# creates it, so it would block every release push. This question has no such window.
#
# WHY IT IS A GATE. v0.242.1 was bumped, merged with all gates and CI green, and shipped
# NO Release: auto-release builds its body from the changelog section, found none, did
# nothing, and reported success. `--check` asks about documented versions; `--audit`
# asks about existing Releases; that version had neither, so it fell between both and
# every mechanism read green while a consumer updated to it off main.
#
# PARITY CANNOT SEE THIS LINE, AND THAT IS NOT A TYPO. `check_gate_parity.py` matches
# `scripts/(check_[a-z0-9_]+\.py)` in both directions, so any gate whose script is not
# named `check_*` is invisible to it. Verified 2026-09-22: after adding this gate to BOTH
# validate.yml and this file, parity still reported "all 22 CI gates are in the local set"
# — it had compared neither entry. The same blindness covers `validate_canvas.py`, which
# runs in CI and is not in this file.
# **So this line and its validate.yml step must be kept in sync BY HAND.** Filed upstream
# rather than fixed here, because broadening the pattern turns the gate red on
# `validate_canvas.py`, which is real pre-existing drift and a separate decision.
