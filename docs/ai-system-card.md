# AI System Card — Mycelium

**A candid description of how Mycelium uses AI, what it does and doesn't do, and how to contest its outputs.**

This card adapts Mitchell et al. (2019) *Model Cards for Model Reporting* to an `agent_runtime_target` product — a framework operated *by* an AI runtime (Claude Code, Codex, Cursor, etc.) rather than one that embeds an AI library. The model details belong to your runtime vendor; what's described here is **Mycelium's recommendation logic** layered over that model.

This is not a marketing document, a technical whitepaper, or a compliance certificate. Read it before relying on Mycelium's recommendations for substantive decisions.

## 2. Intended use

- **Primary use:** Guide solo developers and small teams through the full product-development lifecycle (purpose → strategy → opportunity → solution → delivery → market) with theory citations, evidence gates, and a self-learning correction trail. Operated by an AI agent runtime; Mycelium provides the framing the agent applies.
- **Intended users:** Developers comfortable working with an AI agent (Claude Code, Codex, Cursor, etc.) who want a discovery-first, theory-grounded process with explicit evidence gates. **Risk-aware builders** — those burned by building the wrong thing OR cautious enough to want to avoid it (see `canvas/landscape.yml` strategic positioning).
- **Intended context:** Used during active product development sessions. The agent works from Mycelium's operating contract (handed to it by a hook at the start of every session), its skills and the project's canvas state on every task; recommendations land mid-session rather than as a one-shot setup. **Two operational modes:** *interactive* (a human is present and decides — the default) and *autonomous* (a declared, headless / agent-to-agent run where the agent answers framework prompts itself under a documented substitution discipline; see `engine/autonomous-mode.md`). Autonomous mode is opt-in **by explicit declaration only** — non-interactive detection alone never activates it, and a present human always outranks the flag.
- **What happens at the session's boundaries (since 0.181.0 to 0.244.0, September 2026, and 0.322.0).** Seven behaviours change what the person sees without being asked:
  - *A framework turn cannot end without one next action.* A blocking Stop hook (`next-action-check.sh`, contract rule 12) refuses to end any turn in which a Mycelium skill ran unless the last line begins `Next:`. The agent is held, not the human; the human sees exactly one proposed action.
  - *One proposal per boundary, delivered to the human.* At session start the framework computes its advisories, and `next_item.py` picks ONE (a fired closing-path proposal first, then a muted advisory awaiting a ruling, then the oldest still-firing advisory with a runnable command) and sends it as a `systemMessage` on resume and fork. The Stop hook repeats it once if nothing followed. Every later reader of the stored item (the resume, prompt and Stop lines) stays silent once it is settled: ruled in the ledger or, for a fired proposal, in the record, or written by another release (0.288.1). The verbs are fixed: run, rule, snooze-until a date, drop.
  - *A due review is computed, not remembered.* Session start evaluates which periodic reviews have come due and relays one line each — a reply owed on an outreach task, a pre-registered read whose date has passed, and since 0.231.2 a doctrine retrospective (`check_doctrine_due.py`: a diamond completed since the last review, or a climate prediction past its horizon with no outcome). Each is advisory and exits 0 either way. **Two of these deliberately distinguish "could not look" from "nothing due"**, and report an unreadable register as `UNREADABLE ... did NOT run` rather than as silence — for a check whose subject is a register nobody reads, reporting an unreadable one as OK would be the failure the check exists to prevent. The doctrine check also reports "no diamond has completed yet, so the trigger cannot fire" as its own distinct state, explicitly not as "doctrine is current".
  - *Advisories that are ignored mute themselves.* The advisory ledger (`advisory_ledger.py`, 0.184.0) records at every session start whether each advisory's condition cleared since the last one. An advisory still firing on seven calendar days in a row with no change (days, not sessions: a busy day opens many sessions and would otherwise mute a check the afternoon it first fired) is muted to one line and put on the human's desk as a ruling; it stays muted until ruled. This is deliberate alarm-fatigue control and it means a warning can go quiet without the condition being fixed. Since 0.312.0 quiet is not permanent: a muted, dropped or snoozed advisory whose count rises past where it was muted or ruled speaks again, once, with its own text, so a new instance of a condition someone accepted is not announced to nobody. An advisory its own check forbids clearing mutes without asking for a ruling. The `report` verb lists what is muted.
  - *An unfinished discovery is named at session start (0.244.0).* When setup has run but `purpose.yml` has no purpose statement, and either an interview is half-done or diamonds exist anyway, SessionStart adds one line offering to finish `/mycelium:start` from the saved answers. A nudge, never a block; it found its reason in an end-to-end run where an interrupted interview left later work with no purpose to answer to.
  - *A project that deploys is asked whether something is already live (0.322.0).* When the repository shows the project deploys (a host's config file such as `vercel.json`, `fly.toml` or a `Procfile`, a `Dockerfile` beside a compose file, or a workflow that runs a deploy) and no diamond carries an exposure record, the one proposal at session start is a question, unless a fired closing-path proposal or a pending migration of old records leads that session: is something from this project already in front of real people? A yes is recorded as an exposure record marked `reconstructed`, with no gate passed, so the Security and Privacy checks have something to look at; while no open diamond carries that work, the yes is kept in the advisory ledger in the person's words and the record is still owed. A no is recorded in the advisory ledger and the question stops. `/mycelium:adopt` asks the same when it reads an existing project. It never blocks, and no gate reads the sign or the answer. **What the sign does not show:** a deploy config means the project can deploy, not that it is live, which is why this is a question and never a finding; and a project that deploys nothing from the repository (a service run by hand, a document product, a host set up only in its own dashboard) shows no sign and is not asked. A no is final until the person says otherwise: nothing asks again if the work goes live later by hand. It found its reason in an end-to-end run where a product was live at two sites, with real people's data, for six sessions, outside a release gate that judges only the deploys the agent runs.
  - *A closing-path proposal carries a ruling slot.* When a named input a diamond was waiting on lands, the framework writes a `CLOSING PATH FIRED` proposal on the diamond and waits for a human ruling there (0.187.0, 0.197.0). It never moves the diamond itself. The stored path is re-derived at every session start, and since 0.322.1 that never overwrites what a person wrote inside it: where the stored block holds a key or an item the framework does not write, the block is left as it is and session start says so (`CLOSING PATH NOT STORED`), naming the diamond, the place and the keys such content can live under. Until 0.322.1 the next session start removed it and said nothing.
- **What reaches the agent from the canvas is delimited as data.** Task objectives, NEXT ITEM proposals and research-guard excerpts quoted from canvas files are wrapped as `<untrusted_user_content>` before they reach the agent, and a literal closing tag inside them is defanged (0.172.0, 0.193.0). In a repo with more than one author, a canvas edit is otherwise a session-start instruction.
- **Out-of-scope use:**
  - Not a legal or compliance certification tool. `/regulatory-review`, `/privacy-check`, `/threat-model` raise awareness — they don't replace qualified counsel.
  - Not a substitute for actual user research. The framework can structure interviews and audit evidence, but the evidence has to come from real users.
  - Not for safety-critical AI decisions (medical, legal, financial). Mycelium's quality gates are appropriate to product-development work, not high-risk AI deployment.
  - Not a replacement for engineering judgment. The framework's recommendations are starting points; the developer remains the decider.

## 3. Model details

This is the agent-runtime-target case: **Mycelium does not embed an AI model.** It is operated by an AI agent runtime that the user chooses (typically Claude Code with Anthropic's Claude). Model details belong to the runtime vendor and that vendor's own documentation.

What Mycelium contributes on top of the runtime:
- **Instructions:** the operating contract (`engine/agent-operating-contract.md`), which a session-start hook hands the agent, in four parts, at the start of every session. The plugin has no `CLAUDE.md` of its own for the runtime to load and puts none in your project; the `CLAUDE.md` at the root of Mycelium's repository is for people working on Mycelium itself, and the three under `domains/` are reference the contract points to. The contract defines mandatory protocols (Pre-Task, Pre-Ship, Post-Task) and Communication Rules (plain-language-first, inline attribution, learning-capture prompts).
- **Skills:** 63 skills — markdown SKILL.md files in `plugins/mycelium/skills/` (loaded from the installed plugin) — define structured procedures the agent invokes by name (`/interview`, `/diamond-progress`, `/xai-check`, etc.).
- **Theory-gated state:** `.claude/canvas/*.yml` files persist evidence-supported product state; gates in `plugins/mycelium/engine/theory-gates.md` block a decision a diamond records (`set_target` through `close`) without sufficient evidence, and a recorded decision cannot be removed or rewritten (v0.309.1).
- **Corrections / patterns / warnings memory:** `.claude/memory/` accumulates failures (`corrections.md`), successes (`patterns.md`), and CI signals (`warnings-log.md`). Read before every task.
- **Hooks:** runtime-level enforcement, 32 shell hooks under `plugins/mycelium/hooks/` registered in three runtime manifests (one, `gate-override-check.sh`, in `hooks.json` only, since 0.316.0: it says when another Claude Code extension overruled a refusal, and the other runtimes have no mods) (`hooks.json`, `hooks.codex.json`, `hooks.cursor.json`; the full table is `hooks/README.md`), plus, since 0.286.0, `hooks.codex-plugin.json`, generated from `hooks.codex.json`, which Codex CLI reads for a marketplace install through `.codex-plugin/plugin.json`. These block a tool call before it runs: `gate.sh`, `discovery-gate.sh`, `scale-lock-gate.sh`, `exposure-gate.sh`, `brownfield-gate.sh`, `scope-gate.sh`, `framework-guard.sh`, `autonomous-evidence-guard.sh`, `bash-state-guard.sh`, and since 0.281.0 `guard-state-gate.sh` (which in every project asks the human before the agent writes a file that switches a gate off, and refuses it in a permission mode where nobody is asked, and since 0.286.0 on Codex, whose hooks cannot ask), `scale-lock-gate.sh`, `exposure-gate.sh`, `bash-state-guard.sh` and `guard-state-gate.sh` at a 10 s timeout and the rest at 30 s, all failing closed on broken state since 0.196.0 except where named below. **Since 0.322.1 a gate that cannot run refuses the call instead of letting it through** (maintainer ruling 2026-10-11). Claude Code lets a tool call through when a hook cannot start, reaches its timeout, exits with a status other than 0 or 2, or prints output it cannot read, so until 0.322.1 every gate here let the call through in those cases, whatever its own script did on broken state. Each of the gates named above except `bash-state-guard.sh` now carries `"onFailure": "block"` in `hooks.json`, and Claude Code then refuses the call and names the hook (the one list of which hooks carry it is `hooks/pretooluse-on-failure.txt`; `bash-state-guard.sh` runs before every shell command, stays open when it cannot run, and says so). **What this changes for a user:** on a slow or busy machine where a gate reaches its timeout, every write that gate covers is refused until that is fixed, and shell commands with it, because eight of the nine gates also run on Bash; the same holds where the hook cannot start. The maintainer accepted that cost. **It bites only in a project that uses Mycelium** (a second ruling the same day, "Block only in Mycelium projects"): since 0.318.0 Mycelium does nothing in a project with neither `.claude/canvas/` nor `.claude/diamonds/`, but that exit is inside each script and needs the script to start, so each of these commands now tests for the two folders first and leaves before the hook is started when neither is there. One limit is left, and the maintainer accepted it: that test is read by a POSIX shell (`sh` on macOS and Linux, Git Bash on Windows), and on Windows without Git Bash Claude Code hands the command to PowerShell, which cannot read it, so there the call is refused in every project the plugin is enabled in. It needs Claude Code 2.1.295 or later: an older version does not have the setting, and there a gate that cannot run lets the call through as before. Codex CLI documents no such setting, and Cursor's own (`failClosed`) is set on `gate.sh` only, as it was, so on those two runtimes nothing changed. A gate that runs, exits 0 and says nothing is still an allow: the setting does not change what a script decides. **Since 0.326.0 `shell-safety-guard.sh` also refuses two shell shapes** its warning was measured not to stop: a pipeline ending in a filter and joined by `&&` to `git commit` or `git push` (the filter's exit status hides a failing check), and a scripted multi-file edit that can half-apply. Each refusal names a one-line rewrite and is recorded in the denial ledger. Like `bash-state-guard.sh` it runs before every shell command and stays open when it cannot run (`continue` in `hooks/pretooluse-on-failure.txt`); its other rules only warn. The rest advise, log, or shape the session's boundaries (§2). One of the advisory ones speaks on every prompt of an uninitialized project: since 0.222.0 `preflight.sh` tells the model up front that `discovery-gate.sh` will refuse new source files until a purpose, a diamond or the user's recorded skip exists, and goes silent once one does. **Since 0.245.0 each diamond scale opens only on what its parent has established** (a purpose before strategy, a desired outcome before opportunities, a target opportunity with evidence before a solution, medium confidence before delivery, launch data before a market diamond; `engine/diamond-rules.md`, Entry locks). `scale-lock-gate.sh` refuses a write that adds a diamond before its lock holds (since 0.279.0 the advisory `exposure-change.sh` also tells the agent at once when a write to the diamonds file makes the work not ready for real people, rather than at the next prompt), and `discovery-gate.sh` gains a second stage: once discovery is engaged, a new source file is refused until an L3, L4 or L5 diamond whose whole chain holds is open. Both name what is missing. **Since 0.270.0 the product need not be code:** a project records `product_paths` (where its own files live, such as a service's documents or a course's lessons), and a new file there is refused the same way whatever its kind; the next item asks for the paths once an L0 exists, because an end-to-end run of a service with no software wrote its whole client pack under an L0 while the gate, knowing only code extensions, stayed silent. **Since 0.267.0-0.268.0 the scale lock also judges how an L3's learning delivery changes and ends**: a completion written straight into the completed list passes the same gates as any move, an audience change once the L3 delivers is recorded with its kind (a release to everyone needs an L4), and the L3 completes by recording how its delivery ended. The user alone can override, per diamond (`scale-lock-ack`) or for untracked work (`delivery-skip-ack`); the agent writing either file is asked first. **Since 0.293.0 the delivery skip-ack is a dated, scoped record**: it lifts the build gate only for the paths it names, a release only when it says so, expires after 30 days by default, and every use is logged in `.claude/state/skip-ack-uses.jsonl`; setup keeps it in git. Until then the file's mere existence lifted both gates for all work, forever, and it was gitignored. An old bare file is honoured for 14 days, with a warning at each use. **Since 0.294.0 the work that reaches people is recorded on its diamond** (`exposures`: audience, channel, data class, end date, consent, the gates passed for it); a write that adds one with personal or sensitive data asks the person, and `scale_locks.py --exposures` reports the gaps. **Since 0.295.0 the release gate reads them**: one current exposure record (in date, its gates passed for it) allows a release, several ask the person which, none refuses; since 0.306.0 a project with no records has nothing that covers a release, because the phase is no longer read: where a diamond is comes from the decisions it records, and `migrate_phase.py` turns an old recorded phase into them. **Since 0.321.0 the release path also gives advice it never enforces**: when a current exposure record has no harms check recorded on it (`harms_check`: date, verdict, note), a release the gate allows carries one line of context to the agent naming `/mycelium:harms-check`, the same line is in the readiness report, and the gate's refusal names the check beside the required ones. No verdict, recorded or missing, changes what is allowed; a Happier-negative verdict is repeated to the agent at release so the person hears it and decides. **Since 0.248.0 a diamond moves forward only with a record**: each transition needs its required gates passed and a history entry, so the canvas shows how a diamond got where it is. **Since 0.247.0 no scale is skipped**: opportunities wait for a recorded strategy (an L1 diamond, a North Star, the landscape), solutions for an opportunity cycle, and Security and Privacy count as passed only with a threat model and a privacy assessment on record, not a status word. **Since 0.246.0 the phase follows the work:** new code needs that cycle in Develop with Four Risks and Privacy passed, and `exposure-gate.sh` refuses a deploy or publish the agent runs until it is in Deliver with Security, Privacy and Service Quality passed; a deploy the user runs is covered by an always-on rule, not a hook. **A pilot is not exempt**, because anything user-facing that holds data can let strangers in or leak it out. **What this changes for a user:** building starts later than before on a fresh project, by design, because an end-to-end dogfood run shipped a whole release under an L0 in discover. **Without PyYAML (since 0.290.0) the build and release gates refuse and name the fix**: `/mycelium:setup` offers to install PyYAML for Mycelium only, in the plugin's data directory, and the gates use that environment when the `python3` on PATH has none. Until 0.290.0 the release gate allowed in that state, and the build gate refused for a false reason (it read the project as undiscovered). The scale-lock gate on the diamonds file still allows without PyYAML, and `preflight.sh` says so on every prompt. **Since 0.318.0 no hook does anything in a project with neither `.claude/canvas/` nor `.claude/diamonds/`** (founder ruling after Anthropic's plugin directory review of v0.317.4): no gate, no output, no log, so a fresh repo is not gated before `/mycelium:start` or setup creates one of those, including by the cold-project discovery gate described above; the hooks only stamp a liveness marker in the temp folder. Removing those folders is then the widest off-switch there is, so `guard-state-gate.sh` asks the person before the agent removes them (`rm`, `rmdir`, `mv`, `git rm`, an MCP move), and refuses where nobody is asked. Also since 0.318.0 the release gate answers a project with no diamonds file before it needs PyYAML: nothing there is Mycelium's to check, so a machine without PyYAML no longer refuses deploys and publishes in projects that never used Mycelium (Anthropic plugin directory review of v0.317.4). **The release gate also counts tunnels (ngrok, cloudflared, tailscale funnel, `ssh -R`) and a plain `git push` when the project's host publishes what is pushed** (Vercel, Netlify, a workflow that deploys on push). **What else it reads as a release, since no newcomer page listed it before 0.322.3:** a host's deploy command (`fly deploy`, `netlify deploy`, `vercel --prod`, `railway up`, `gcloud ... deploy`, `aws ... deploy`, `serverless deploy`), `kubectl apply`, `helm install` or `upgrade`, `terraform apply`, `pulumi up`, `docker push`, a copy to a bucket (`aws s3 sync`, `cp` to `s3://`), `scp` or `rsync` to another host, a package publish (`npm publish`, `twine upload`, `cargo publish`), a remote restart over `ssh`, and any command or script named `deploy` or `publish` (`npm run deploy`, `./deploy.sh`). That last rule over-matches local scripts on purpose. A command on this list that puts nothing in front of people (an `rsync` to a backup host) is asked about or refused like the rest. The gate no longer counts a release verb that only appears in a heredoc body, a commit message or an echo. **Since 0.291.0 editing product code counts as building** once discovery is engaged (Edit, MultiEdit and the MCP edit tool, not only new files), except under declared `prototype_paths`, which are free to write and edit; releasing prototype code is still gated. **Until 0.321.1 that was true of those three tools only**: a whole-file write over an existing product file, a notebook edit and a shell edit passed the build gate. Also since 0.322.5 `vercel --prod` reaches the release checker: the hook's word filter had no word for it, so the checker that lists it never ran. **Since 0.322.6 a Mycelium switch in a Claude Code settings file is the person's to set.** Claude Code takes environment variables from the `env` block of `.claude/settings.json`, `.claude/settings.local.json` and `~/.claude/settings.json`, and two more keys there end every hook (`disableAllHooks`, and `enabledPlugins` with the plugin set to false). Three Mycelium variables loosen a stop, and until 0.322.6 no gate looked at a write to those files: a tool call that put `MYCELIUM_GUARD_STATE_EDIT` into `settings.local.json` drew no decision (replayed 2026-10-12 on 0.322.1). Now `guard-state-gate.sh` works out what a file tool would leave in a settings file, and when that is a new switch (any `MYCELIUM_*` variable, `CLAUDE_PROJECT_DIR`, `CLAUDE_PLUGIN_ROOT`, or either key) it asks the person, or refuses where nobody is asked; an edit that sets none is not asked about. `bash-state-guard.sh` compares the switches before and after every shell command and takes a new one out again, keeping the rest of the file, the file in the home folder included (maintainer's ruling 2026-10-12); the plugin switched off in `enabledPlugins` is reported and left, because Claude Code's own plugin commands write that key. Not shown: any of this in a live session, in any permission mode; that hook commands receive the `env` block and that it is re-read mid-session is Claude Code's documentation, not a test of ours. Not covered: a variable that changes how a shell starts (`BASH_ENV`, `PATH`), an edit made through a symlink whose name does not say `settings.json`, the settings files of Cursor and Codex, and managed or command-line settings.

The runtime model is therefore **the actual decision-maker** — except in a declared autonomous run, where a documented substitution discipline (`engine/autonomous-mode.md`) plus the autonomous-evidence-guard govern what the agent may decide and persist without a human in the loop.

## 4. Performance and limitations

### What Mycelium does well

- **Discovery and strategy.** Heavy mechanism for L0 Purpose, L1 Strategy, L2 Opportunity work — JTBD, OST, Wardley, scenarios, user-needs. Strongest convergent-validity from external practitioners (Bentes/BDSK, Hoskins, Wardley, Skelton — see `corrections.md` cross-references).
- **Self-correction.** When the agent makes a mistake, the framework-guard / reflexion hooks catch it; corrections.md logs it; recurring patterns graduate to mechanism. The Lopopolo reframe — "every interaction is a failure of the harness" — is the load-bearing principle.
- **Evidence discipline.** Theory gates require explicit evidence types per scale; source-class taxonomy (external_human / external_data / internal_stakeholder / internal_desk / internal_simulated) prevents desk-research-only confidence climbs.

### Known limitations (honest list)

- **Prompt-shaped, not code-shaped.** The framework is markdown read by the agent, not executable code. Some checks (e.g., the `delivery-bootstrap` Step 1c detector) have no automated coverage proof. A blind spot for `agent_runtime_target` products was caught only by dogfooding `/xai-check` against Mycelium itself (corrections.md 2026-05-04).
- **Verbose first-time output.** New users can find the framework's preambles, theory citations, and protocol enumeration overwhelming. Sprint-mode interview helps but the underlying ceremony is real.
- **Process cliff after `/interview`.** A 2026-04-30 correction documented that 75% of a session can lose Mycelium structure after onboarding. Sprint-mode shipped; lightweight discovery-to-delivery continuation mode is still partial.
- **Opinionated.** Mycelium bakes in specific framework choices (Torres/CDH, Cagan/Inspired, Hoskins/Scenarios, Skelton/Team Topologies, Cynefin, GIST). Teams that prefer different frameworks will need to override — not all overrides are graceful.
- **Solo / small-team optimized.** The orchestration patterns target single-agent + single-developer dynamics. Multi-developer, multi-agent coordination is documented in `orchestration/` but less battle-tested.
- **The build gate does not see files that a command writes.** The stop on a first source file and the hold on product code both judge a write they can read: the agent's edit tools and plain shell writes. A command the agent runs that writes the files itself gives them nothing to read. Replayed on 0.322.3 and again on 0.322.6, in a project where a plain redirect to a new source file is refused, each of these passed with nothing said: a scaffolder, `npm init`, `cargo new`, `git clone`, `curl -o`, a script that writes a source file, `patch`, `git apply`. Writes through another tool server were reported by a reader and not checked. A comparison of the project's files before and after each shell command would close it; that work has desk tests behind it and is not built (parked 2026-10-12, waiting to learn which platforms real users are on). Until then README.md says the limit beside the claim. Claude Code's own checkpoints do not track files a shell command changed either.
- **The scope hold sees the writes it can read, and holds only where folders were named.** Since 0.324.0 a delivery cycle (an L4) names the folders it may write to when it commits to build (`in_scope_paths` on its record in `.claude/diamonds/active.yml`), and while it is open a write outside them is put to the person; where nobody can be asked it is refused. Three limits. A command that writes files itself (a scaffolder, a clone) names no target the hold can read, as for the build gate above; if such a command changes the folders themselves, the diamonds file is put back afterwards and the person is told, which a process the command leaves running, or a script written to rewrite Mycelium's own copy as well, gets past. "No hold for this one" (an empty list) is a legal answer, given by the person. And a cycle that committed to build before 0.324.0 names nothing and is not held; session start says so. Until 0.324.0 the folders were read from `.claude/state/active-execution.json`, which nothing Mycelium ships wrote, so the hold was never on in a plugin install (a blind reader of the installed plugin, dogfood 2026-10-11); that file is no longer read, and while one exists product writes are refused with what to do. Shown by a replay of fourteen writes through the shipped hook, kept as a test; the same sheet was first read against a scratch copy by someone who did not write it. Not shown: a real delivery cycle run under it, or any builder outside the project.
- **A shell command's change to the diamonds file is put back (since 0.325.0).** The entry locks, the decision gates and the questions put to the person run on the edit tools. Until 0.325.0 the shell guard read the command's text, so a script that opened `.claude/diamonds/active.yml` itself changed it unseen (dogfood 2026-10-14: a whole definition of done replaced, nothing said). Now the file is compared around every shell command; a change is put back, the command's version kept under `.claude/state/bash-guard/put-back/`, and the person told. Excepted: Mycelium's own writers run on their own, the person's override, and git leaving the file as committed at HEAD unless the same command committed a change to it. Limits: a process the command leaves running, a script that also rewrites Mycelium's copy, and a file committed by one command and restored from HEAD by the next. Shown by tests that drive both halves around each case, red on 0.324.0. Not shown in 0.325.0: a replay in a real session, and the first one found the next gap. **Since 0.325.1 Mycelium's own write while a command runs is not the command's**: session start runs `derive_closing_path.py --all --write` in the background, and on 0.325.0 a read-only `git log` running meanwhile was told it had changed the file, which was put back mid-write (dogfood 2026-10-15). The script now applies its own edit to the guard's copies before it writes, so only what the command did is put back.
- **Vendor-runtime dependent.** AI quality is upstream of Mycelium. If Claude (or whichever runtime) produces a confidently-wrong output, the framework's gates catch *some* but not all of those failures. corrections.md exists precisely because gates miss things.
- **Autonomous-mode evidence integrity is model-dependent.** Run headless/autonomously, the agent substitutes for the absent human. The evidence-integrity boundary (no fabricated external evidence) is *enforced as mechanism* by `autonomous-evidence-guard` for the cardinal canvas write-path, but is otherwise prose-only and **does not transfer below Fable 5** — a Haiku 4.5 run (opp-011 Stage A, 2026-06-11) fabricated `external_human` interview results and did not recognize it had. **Operating rule: do not run autonomous mode on a sub-Fable-5 model without a present human.** Residual unenforced gaps: Bash-heredoc writes, in-conversation prose fabrication, non-canonical paths (covered by the model-tier restriction, not the guard).

### Known foreseeable misuse

- Treating skill suggestions as authoritative without applying judgment. Skills are starting points; the developer decides.
- Skipping pre-ship analysis on substantive framework work. This was identified as a recurring agent-behavior failure (corrections.md 2026-05-04 RECURRING entry); the new G-P-pre Mandatory Pre-Ship Protocol is the convention-layer fix.
- Treating corrections.md as a graveyard for issues to defer. The cleanup-cycle pattern is for *batched* cleanup, not indefinite deferral. See `feedback_no_tech_debt_deferral.md`.

### Evaluation methodology

- **Self-eval.** `.claude/evals/assumption-tests/` and `.claude/evals/scenarios/` track behavioral hypotheses with pre-committed pass/iterate/kill criteria. The original `2026-05-04-xai-inline-attribution` eval closed 2026-05-12 at session 11 with verdict **INSTRUMENT FAILED**: agent self-report didn't reliably log per-session data (sister failure to relay-norms). The rule itself (the `(per: <source>)` inline-attribution requirement) was preserved — absence of evidence is not evidence of failure, and the citations that did appear were load-bearing rather than theatre (Lanham et al. 2023 faithfulness frame). The measurement instrument was replaced by C1 (v0.23.8): `hooks/read-log.sh` (PostToolUse on Read) captures every read mechanically, and `scripts/verify_citations.py` cross-references file-shaped citations in agent output against the captured log. At time of writing, the C1 read-log carries 376 entries since 2026-05-12 in the roadmap dogfood project; no formal faithfulness audit has been run against captured data yet — that requires a text sample with citations and is the next audit step (Juniors.dev cohort sessions are the natural source per the original eval's bias-guard).
- **Cycle history.** `.claude/canvas/cycle-history.yml` captures completed leaf lifecycles for calibration. Active maintenance: cycles close routinely; framework-health quarterly audit is the canonical synthesis surface.
- **Framework reflexion.** `/framework-health` runs quarterly self-assessment of process effectiveness (cycle velocity, discard trends, confidence calibration, gate effectiveness); last executed 2026-07-05 in the roadmap dogfood project.
- **External evaluation.** Convergent validity comes from external practitioner feedback (canvas evidence trails). Application-grounded user testing is pending, and no external cohort exists today: the Juniors.dev pilot this card used to name as the next test was stopped on 2026-08-14. The next test is the next facilitated run with someone outside the project.

## 5. Explainability

- **Disclosure surface.** This system card + the README's product positioning + CLAUDE.md's frontmatter version line. Users running Claude Code with Mycelium installed know they're operating an AI runtime that's been instructed by Mycelium; the runtime itself discloses AI nature (Anthropic's own disclosure). **Autonomous operation is disclosed and gated:** Mycelium can run with no human in the loop, but only under an explicit operator declaration (`engine/autonomous-mode.md`); such runs keep a mandatory substitution ledger and are subject to the evidence-integrity guard, so a human reviewing the output can see exactly which entries a machine produced and confirm no fabricated external evidence was persisted.
- **Per-decision rationale.** The framework's operating contract (`engine/agent-operating-contract.md` rule 4, injected at every session start in plugin form; originally a CLAUDE.md Communication Rule, added 2026-05-04) requires the agent to cite the trigger of any non-trivial move with `(per: <source>)`. **Measured 2026-09-14 on the dogfood project: across the twelve most recent session transcripts the form appeared three times.** Measured again on 2026-10-03: three sessions in twelve. As prose the rule was rarely followed, so since 0.311.0 it has a mechanism at the one place a framework turn always makes a recommendation: `hooks/next-action-check.sh` blocks the end of a framework turn (a Mycelium skill the agent ran or the person typed) until its closing `Next:` line carries `(per: <source>)`. Everywhere else the inline form is still the agent's discipline and should be read as advisory; the durable rationale surface remains the decision log (`.claude/harness/decision-log.md`, whose entries carry a structured `why_not_alternatives` field) and the per-hook advisories, each of which names the measurement it fired on. Whether the requirement changes behaviour is measured at the next audit, from `.claude/state/next-action-check-fires.jsonl` (outcome `blocked-no-per`) and the same transcript count. Sources include corrections.md entries, canvas evidence, theory gates, patterns, decision-log entries. Faithfulness is **mechanically capturable, and audited on demand rather than continuously** — the C1 instrument is two halves with different automation status (v0.23.8): `hooks/read-log.sh` is a PostToolUse hook and captures every file the agent opens automatically, observed through the Read tool and, since v0.143.0, inferred from shell commands (on Codex CLI, which has no Read tool, the shell is the only route, logged since 0.286.2), while `scripts/verify_citations.py` — the half that cross-references file-shaped citations against that log — is **operator-run by design** (its own header defers automatic Stop-hook integration until the false-positive rate has been measured). Sample-against-population audits are the next step (see §4 evaluation methodology).

> Corrected 2026-07-26. This sentence previously read "Faithfulness is verified mechanically by the C1 instrument", which overstated a published claim: it implied continuous automatic verification when only the capture half runs unattended. The audit half has never been wired, deliberately — but a system card is exactly where that distinction has to be exact, and a reader could not have drawn it from the old wording. Caught by `check_wiring.py` Rule D, which requires any prose claiming a named script is automatic to point at a script that actually has a caller.
- **An overruled refusal is disclosed (since 0.316.0).** Claude Code Mods can approve a tool call that a Mycelium gate refused. When a refused call runs anyway, `gate-override-check.sh` tells the person (`systemMessage`) and the agent that the gate was overruled, so neither the logs nor the agent report the refusal as having held. It cannot say which extension approved the call; PostToolUse input does not carry that.
- **Confidence signaling.** Every confidence claim must include level + evidence type + WHY appropriate + what would increase it (the operating contract's Communication Rules). This is calibrated, not vibes-based.
- **Fidelity caveat.** When the agent emits rationales, they are the agent's articulation of what drove its move — not a guaranteed audit of the underlying model's computation (Lanham et al. 2023). The original self-report eval treated theatre as a kill criterion; it was retired 2026-05-12 because the instrument (agent self-recording) failed, not because the rule did. The current instrument (C1 mechanical capture) audits file-shaped citations against actual read events; theatre would surface as citations to files never read.

## 6. Recourse

- **How a user contests an agent recommendation.** File an entry in `.claude/memory/corrections.md` describing the mistake. Format defined in the file's header. The entry stays in the user's repo (committed) and feeds into `/corrections-audit` for pattern detection. The operating contract tells the agent to read it before a task; nothing enforces that read, and a long file is not read whole (see Service-level commitment below). For framework-level issues, open an issue at github.com/haabe/mycelium/issues.
- **How a user overrides a scale lock (since 0.245.0).** When a lock is wrong for their case, the user writes one line in `.claude/state/scale-lock-ack`, `<id> <scale> <YYYY-MM-DD> <their own words>`, and that diamond opens past its lock at that scale; untracked building is recorded in `.claude/state/delivery-skip-ack`. Both are guard state: the agent writing either is asked first (on Codex, which cannot ask, refused), so the override is the user's decision and it is on the record. **Until 0.321.1 that held only for a write the hook could read**: a shell command that wrote one of these files through a variable was not asked about. Since 0.321.1 the files that switch a stop off are compared before and after every shell command, and a change the user was not asked about is put back and reported to them (`bash-state-guard.sh`); a write that lands after the command has returned (a background job) is not caught by that comparison. `scale_locks.py --check` keeps reporting what the overridden diamond still lacks. No override waives what an L4 delivers: it names its solution (or its L3's front runner) whenever the L3 holds more than one (since 0.307.6). **Since 0.322.2 the override travels with the repository.** Until then `scale-lock-ack` was the one decision file the state folder's ignore file did not keep in git, so a fresh clone had the lock closed again with no record of the override; that was an oversight. A project whose ignore file was written by an earlier version still ignores it, because Mycelium never rewrites an ignore file that exists: session start says so (`DECISION FILE NOT IN GIT`, for any of the five decision files) with the line to add, and whether to commit the file is the user's to decide.
- **When another extension overrides a gate (since 0.316.0).** A Claude Code mod can approve a call a Mycelium gate refused, without the user writing any ack. That override is not hidden: the person is told when it happens, and it is logged (`gate-override-fires.jsonl`). An organisation that needs the gates to hold can set `allowManagedModsOnly` or register the hooks in managed settings, which a mod cannot overrule.
- **What has no override: the secret scan, which since 0.323.0 runs at the commit and the push.** Until 0.323.0 Mycelium scanned what the agent WROTE to a file, with a short list of its own. Replayed 2026-10-12: an unquoted `KEY=value` passed, an env file was treated like source code, and nothing looked at what was staged. By the maintainer's rulings of that day the write-time scan is gone and three scans take its place (`scripts/commit_scan.py`): before the agent's `git commit`, what the commit would take (the index; with `-a` or a named path, the tracked files as on disk); after any shell command, commits the command itself made by any route, read from HEAD's reflog; before the agent's `git push`, every commit on a local branch that is on no remote. A finding refuses the commit or the push and names file and line, never the value; a finding in a commit already made is reported, the commit is left as it is, and the push is where it stops. **The scanner is gitleaks when it is installed.** When it is not, Mycelium's own short list (`scripts/_secret_patterns.sh`) runs in its place and the person is told once a session that it is the weaker check. A scan that cannot run refuses, with the scanner's own words (the 0.319.1 rule). There is no Mycelium file or flag that lets a finding through. The scanner has its own ways past one (`.gitleaksignore`, `.gitleaks.toml`, a `gitleaks:allow` comment), and those are guarded: the agent's write of one asks the person, a shell change to the two files is put back. A key typed into a shell command is still refused, by the short list, since it would end up in logs. **What this does not do:** it does not stop the agent writing a key into a file; it does not see a commit or push the person makes in their own terminal unless they let `/mycelium:setup` install its git hook in that clone; it recognises `git commit` and `git push` where a command starts, so a commit made some other way is caught only afterwards and at the push; it scans the repository the command names (the session's folder, the last `cd` before the commit, or `git -C <folder>`), and does not follow a folder held in a variable; and it has been run on macOS only. A `gitleaks:allow` comment added by a shell command, and the scanner's configuration through an environment variable, are not watched.
- **When a gate cannot run and refuses everything (since 0.322.1, Claude Code 2.1.295 or later).** The refusal names the hook and says whether it failed or timed out. Nothing in the project lifts it, because nothing was judged: the way past is to fix what stops the hook (a machine too slow for the 10 s or 30 s timeout, a missing `bash` or `python3`, a broken plugin install), or to turn the plugin off in Claude Code while that is fixed, which is the person's call. It happens only in a project that has `.claude/canvas/` or `.claude/diamonds/`, with one exception: on Windows without Git Bash the command cannot be read at all, and every project the plugin is enabled in is refused until Git Bash is installed or the plugin is turned off. A report is an issue at github.com/haabe/mycelium/issues.
- **Removing Mycelium from a project is the person's call (0.318.0, enforced by the hook since 0.318.3).** Deleting `.claude/canvas` and `.claude/diamonds` switches every hook off. The agent doing it is asked first, and refused where nobody would be asked; doing it yourself in your own terminal is not held.
- **Who reviews the contestation.** The user's own agent reads corrections.md on the next task and adjusts. For escalated patterns: Håvard Bartnes (maintainer) reviews via GitHub issues. There is no automated chatbot in the loop.
- **Service-level commitment.** One-off corrections are written the same day; whether a later session reads them is not enforced. In the maintainer's own project (2026-10-16), the file had grown past what the Read tool accepts and was opened in 12 of 71 sessions, and 86 of 96 recent corrections repeated a lesson already on record; a lesson that became a hook matching its exact shape caught the repeat 10 times in 12. Putting lessons in front of the agent when it acts is open work, not a shipped feature. Recurring entries are tracked as clusters in `.claude/memory/cluster-instances.md`; a cluster that crosses its stated graduation criterion (typically three instances of one root cause) must either graduate to a mechanism or carry a `review_by` date with a written reason, and `check_cluster_reconcile.py` fails at session start when a cluster is past its date or the catalogue is more than five corrections behind the log. That replaced the earlier "next L4 cleanup cycle" commitment, which named a cadence nothing enforced. Rulings on advisories and proposals (§2) are the in-place recourse for the framework's own nudges: `snooze-until` and `drop` are recorded in the advisory ledger, and a ruling on a closing-path proposal is recorded on the diamond, where it is durable; ledger rulings live in `.claude/state/` and are not committed. **Open issues on github.com/haabe/mycelium**: no formal SLA for response time; this is a solo-maintainer project. Acknowledged as a known gap.
- **Logging.** Every contestation is logged in corrections.md (committed to the user's repo). Public-graduation cases (recurring → graduated) are visible in mycelium upstream commit history.

## 7. Privacy and data handling

- **What user data Mycelium handles.** All canvas state, corrections, patterns, decision logs, and evals live in `.claude/` inside the user's own repository. **Mycelium does not send user data to its author or to any service the author runs, and reads no credential from the user's machine.** One automatic hook asks GitHub, through the user's own `gh` login, for the latest CI result on the current branch (off with `MYCELIUM_CI_SIGNAL=off`); everything else that touches the network runs only when the user starts it. The full account, including the few files written outside `.claude/`, is [PRIVACY.md](../PRIVACY.md). The runtime (Claude Code / Codex / Cursor) sends data to its own vendor per that vendor's privacy policy — Mycelium is upstream of that and has no involvement.
- **Retention.** User-side: as long as the user keeps the repo. Vendor-side: per the runtime vendor's policy.
- **Opt-out.** Mycelium collects nothing. The automatic CI check is off with `MYCELIUM_CI_SIGNAL=off`, and the session-start writes to `.claude/diamonds/` with `MYCELIUM_CLOSING_PATH_WRITE=off`. The user's relationship is with the runtime vendor.
- **Sensitive content.** The only ignore file Mycelium writes is `.claude/state/.gitignore`, which keeps its logs out of git. It writes no `.claude/.gitignore` (until 0.322.3 this card described one, a detail of the maintainer's own project). Everything else under `.claude/` (canvas, memory, the decision log) is meant to be committed, so what is recorded there is as public as the repository; since 0.322.3 the secret scan covers writes to those files too. For products built using Mycelium, run `/privacy-check` to assess data flows in the product itself.

**Interview answers in progress (added 0.244.0).** While `/mycelium:start` runs, each question and the user's answer is appended to `.claude/state/interview-in-progress.md` (gitignored, local only) so an interrupted interview can resume; the file is deleted once the brief is rendered and `purpose.yml` is written. It holds the user's own words about their idea and nothing else.

**Reading another local repository (added 0.310.0).** If a project sets `thresholds.yml#thresholds.cycle_recording_arc.release_repo`, the work-recording check that runs at session start reads the version tags of the repository at that path (`git for-each-ref refs/tags`, since 0.319.2), or its commit subjects (`git log --format=%s`) when it has no version tags. That path may be outside the project. It writes nothing there and sends nothing anywhere. Unset, which is the default, it reads only the project's own history.

**State logs (added 0.194.0, security review DL-1262).** Advisory hooks append one JSON line per fire under `.claude/state/`, gitignored by the setup skill: a timestamp, the hook name, a fire count and a signature. Since 0.194.0 the discovery-trigger log records a digest and length of the matching sentence rather than the sentence, so no fragment of a prompt is persisted. The shell-safety log records the warning text the framework wrote, and the absence-claim log records the agent's own claim sentence; neither records the user's prompt. Since 0.204.0 the blocking `gate.sh` also logs two of its five refusals in `gate-block-log.jsonl`, the two that can stop every write in the middle of a session: a preflight stamp gone stale, and a corrections file that changed (timestamp, reason, session id; no content), so the cost of the gate is a count rather than a guess. The other three (a credential in what is being written, a secret scan that could not run, tool input it cannot read) are not in that log; since 0.316.0 all five are counted in the denial ledger described below. Since 0.212.0 the post-write nudge keeps a one-line-per-canvas ledger (session id and canvas file name, no content) so each reminder is issued once per session. **Since 0.234.0 every BLOCKING hook keeps a record, which four of them did not.** `discovery-gate`, `brownfield-gate`, `autonomous-evidence-guard` and the `next-action-check` Stop hook now append one line per block (timestamp, hook name, outcome, and a short label such as the skill that triggered it or the field names that tripped the guard — never a prompt, file contents or the user's words, per the DL-1262 review that shaped these logs). **Why it matters for a reader of this card:** these are mechanisms that can refuse a tool call or refuse to end a turn, and until 0.234.0 how often they did so was unmeasured — `check_retirement_candidates.py` could answer neither of its two questions for 10 of 25 hooks, so 40% of the hook surface, including all four blockers, sat outside the only instrument that asks whether a mechanism still earns its place. **Since 0.236.0 the remaining six advisory hooks also keep a record** — `ci-signal`, `codex-postfailure-shim`, `correction-attribution-guard`, `install-runtime-hooks`, `reflexion-gate` and `shell-safety-guard` — so no shipped hook is now outside the retirement instrument. **What a reader should know about the shape of that record:** it is written on the path where the hook actually produced output, never at entry. Three of the six only find out whether they have anything to say by running a helper, and a row logged at entry would have recorded a fire on every matching tool call — a number that reads as data while being indistinguishable from a mechanism that never discriminates. The rows carry a timestamp, the hook name and the outcome `fired`, and carry NO detail field at all, so nothing of the user's command or prompt is persisted by these six; that is stricter than the shell-safety log described above, which records the framework's own warning text. The writing is shared: `scripts/_hook_fire_log.sh` holds one implementation, so the atomicity, the failure mode and the privacy rule are decided once rather than ten times. **Since 0.250.0 a written canvas or diamonds file is checked against its schema as it lands** (`canvas-schema-check.sh`, PostToolUse, never blocking): it records the outcome only in `canvas-schema-check-fires.jsonl`, and when its optional dependencies are missing it keeps a one-line-per-session ledger of session ids (`canvas-check-skipped`) so it says so once. Neither row holds file contents. **Also since 0.250.0 the next item keeps a count.** `diamond-rulings.json` holds, per diamond id, a phase signature, the machine time it last changed and the session id; `next-item-log.jsonl` holds, per item that left, its id, dates, how many sessions it was shown and whether it was ruled. Since 0.307.7 `diamond-rulings.json` also holds, for a diamond that delivers, a copy of its exposure records (audience, channel, data class, until), which is the user's own canvas text; this card said "No canvas text" here until 0.322.3. Apart from that copy: no canvas text, prompt or user words. **What changes for a reader of this card:** an item unanswered for three sessions is shown to the human with its age and count and a request to decide (run, rule, snooze, or drop if it is wrong), and to the agent once per session beside its first request. It never blocks and never repeats per turn; any ruling resets it. **Since 0.272.0 an item that is Mycelium's own record work is not put to the human as a decision**: recording a test's verdict against the bar it was frozen with is shown to the human as being recorded, and to the agent as its to do now, asking the human only when the bar leaves the result unclear. **Since 0.250.1 it reaches the human once per sitting** (one session on one day), however often the session is resumed, and the end-of-turn "Session: N corrections, M decisions logged." line is shown only when a count changed (`stop-check-counts-shown` holds the session id, the date and the corrections count, nothing else; since 0.252.0 the line is shown once per sitting and again only when corrections change). **Since 0.252.0 the agent is told at the prompt when the work may not yet meet real people** (`MYCELIUM EXPOSURE STATE`), at most twice a sitting: at its first prompt and at its first prompt about an act of going live (since 0.252.1), and that this covers a deploy someone else performs; `exposure-line-said` holds the session id and date only. **Since 0.252.2 the per-prompt hook also reads the prompt to spot the user answering the open next item** ("snooze it", "drop it", "not now") and points the agent at the command that records it; the prompt is matched in memory and nothing of it is stored. **Since 0.253.2 a shell command cannot change diamond state unjudged** (`bash-state-guard.sh`, before and after every shell command): a command that visibly writes `diamonds/active.yml` is refused and pointed to Edit/Write, where the scale locks run; afterwards, any canvas or diamonds file the command changed is schema-checked and a changed diamonds file is judged by the scale locks, with the finding told to the agent. It keeps one snapshot of `diamonds/active.yml` and a timestamp under `.claude/state/bash-guard/`, and a fire log with outcomes only. **Since 0.315.0 the scale-lock gate's block rows say what kind of rule refused** (`scale-lock-fires.jsonl`, detail field): a closed vocabulary from `scale_locks.BLOCK_KINDS` such as `entry_lock` (a parent's record missing) or `decision_gates` (a diamond's own gates), never diamond ids, canvas text or the user's words, so where builders are stopped, and by what, can be counted. **Since 0.316.0 every refusal also lands in one denial ledger** (`denied-calls.jsonl`: timestamp, the refused call's `tool_use_id`, the refusing hook's file name, session id; no tool input or content), and `gate-override-check.sh` keeps `gate-override-fires.jsonl` (outcome `overridden` and the refusing hooks' names) for refused calls that ran anyway. The ledger is trimmed with the other activity logs, after 90 days by default; lookups read its last 2,000 rows. **Corrected in 0.318.0 (Anthropic plugin directory review of v0.317.4).** This paragraph said the six advisory hooks persist nothing of the user's command. That held for their fire rows, not for `reflexion-gate.sh`'s second log, `reflexion-log.jsonl`, which kept 160 characters of each failed command from 0.64.0 (2026-07-26) and 200 of its error output from 0.78.0 (2026-08-03), unmasked, by default. It now keeps the time, exit code and program name; the command and output only with `MYCELIUM_LEDGER_TRIGGER=on`, masked; and the first session on 0.318.0 strips them from older lines. The release log `exposure-uses.jsonl` now masks the release command it keeps. And "gitignored by the setup skill" held only where setup had run: since 0.318.0 every hook that finds `.claude/state/` without its ignore file writes one. Since 0.318.0 the activity logs keep 90 days by default (`MYCELIUM_LOG_RETENTION_DAYS`, `0` keeps all; `prune_state_logs.py` at session start), decision records are never trimmed, and no log is kept at all in a project without Mycelium state. The full list, with what one line of each holds, is in `PRIVACY.md`.

## 8. Ethical considerations

- **Stakeholders affected.** Direct: developers using Mycelium. Indirect: end users of products built using Mycelium (the framework's discovery and quality gates shape what gets shipped).
- **Anticipated harms.** (a) Over-reliance on framework recommendations without judgment — mitigated by the explicit "developer remains the decider" framing throughout. (b) Theatre — performing process without substance, which the framework explicitly guards against (eval kill criteria, Goodhart's-Law commentary in patterns.md, faithfulness audits in /xai-check). (c) Opinionation lock-in — Mycelium's framework choices may not fit all teams; documentation calls this out.
- **Mitigations.** Self-correction loop (corrections.md + /corrections-audit + recurring-≥3 graduation), Lopopolo reframe applied at every recurring-failure point, explicit `validated_functionally` vs `needs_user_testing` tagging in /xai-check output.

## 9. Caveats and recommendations

- **Open questions.** Whether the discovery-first / theory-grounded approach scales beyond solo and small-team contexts (the Juniors.dev pilot named here as the test was stopped on 2026-08-14; no external cohort exists today); whether the framework's verbosity becomes friction at scale; whether agent runtimes other than Claude Code give comparable behavior (agent-agnostic aspiration; not yet tested).
- **Recommended next audit.** This card is re-reviewed annually or after any material change to the framework's recommendation logic (new mandatory protocol, major skill set change, runtime portability work).
- **Last full audit:** 2026-10-03 via `/mycelium:xai-check` against `svc-mycelium` (seventh audit). It found this card's hook-driven sections current and three passages stale for reasons no hook could see: a stopped pilot named as the next test (§4, §9), and this line still naming the fifth audit as the last. The per-audit record of what each audit closed and left open is kept in the maintainer's dogfood project, which is private; this line is the public summary and is replaced at each audit.

**Distribution is unsigned.** The plugin installs through the Claude Code marketplace as a pull of this repository's `main`; there is no artifact signing in that channel, and `/plugin update` takes whatever `main` holds at the time. What stands in for signing: every release is tagged at the commit that set its version, the release job refuses a commit whose validator was red, Actions are pinned to commit SHAs, and CI dependencies are pinned exactly and audited on every push (`pip-audit`, `zizmor`). An adopter who needs stronger provenance should pin the plugin to a release tag. The framework's own STRIDE threat model is [threat-model.md](threat-model.md), last reviewed 2026-05-11.
